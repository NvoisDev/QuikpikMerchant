Implement a full refund flow where:

🚨 NON-NEGOTIABLE RULES

Use new logic layered on top
💳 Refund Behaviour
Customer receives:
Full order total (including delivery + fees)
📦 Stock Restock Logic (CRITICAL)
🧠 Core Principle

Refund = reverse the stock movement

✅ Restock Rules
1. Restock ONLY if stock was previously deducted

Check:

order.status = fulfilled OR completed

👉 Prevent double restocking

2. Restock per order item

For each item:

restock_quantity = refunded_quantity
🔁 Batch-Aware Restocking (IMPORTANT for your system)

If using batches:

Preferred approach:
Restock back into original batch
{
  "product_id": "...",
  "batch_id": "...",
  "quantity": 10
}
If original batch is:
❌ Deleted
❌ Fully depleted / archived

👉 Then:

Create a new batch:
Batch name: "Refund Return"
expiry_date: original OR null
⚠️ Do NOT:
Merge into random batches
Ignore batch tracking
Overwrite batch quantities incorrectly
🔄 Stock Calculation Impact

After restock:

product.total_stock = SUM(all active batch quantities)

👉 Must auto-update (no manual override)

🔁 Partial Refund Handling

If refund is partial:

Restock ONLY refunded items/quantities

Example:

Ordered: 10 units  
Refunded: 4 units  
→ Restock: 4 units
⚠️ Delivery Refund Logic
Delivery has no stock impact
Only affects financials
🧾 Order State Management

Update order:

status = refunded OR partially_refunded

Add:

restock_status = completed

👉 Prevent duplicate restocking

🔐 Idempotency (VERY IMPORTANT)

If refund endpoint is triggered twice:

DO NOT restock twice

Use:

refund_id OR restock_flag
⚙️ Backend Flow
When refund is triggered:
Call Stripe refund API
On success:
Update order status
Reverse commission
Trigger stock restock logic
🧪 Edge Cases

❌ No restock needed

Optional:

reason = damaged
